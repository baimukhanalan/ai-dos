## 1. Что это за продукт

**AI Dos** — не «бот для записи», а **AI Patient Access Platform** для клиник Казахстана: система берёт на себя первую линию общения с пациентом (звонок / чат / веб), понимает запрос, работает с расписанием и записью, а сложные случаи передаёт человеку с готовым контекстом. DamuMed выступает backend-системой записи (подключается по официальному API).

Формула: **Пациент → AI → понимание запроса → правила клиники → запись/решение → сопровождение**. Человек появляется только на исключениях.

Позиционирование и полное видение (V1→V4) зафиксированы в памяти проекта (`product-vision`) и в этом документе, раздел 7.

## 3. Что построено

### 3.1 Лендинг (`src/components/marketing/`)
- Светлая премиальная **зелёная** палитра (кремовый фон, изумруд, приглушённое золото), без тёмной темы.
- **i18n RU / KZ / EN** — переключатель-глобус в хедере, весь текст переведён, выбор сохраняется в localStorage, ставит `<html lang>`. Словарь: `i18n.ts`.
- Сторителлинг-главы (Вечер → Звонок → Голос → Ночь → Границы → Основание → финал), появление блоков при скролле через IntersectionObserver, уважает `prefers-reduced-motion`.
- Кадры интерьеров сгенерированы через Higgsfield (светлые, `public/hero/`).
- Была тяжёлая тёмная скролл-секвенция камеры — **убрана** (давала лаги).

### 3.2 Портал (`src/app/portal/`)
Единый role-aware интерфейс: Разговоры, Голос, **Операции**, Расписание, Пациенты, Клиника, **База знаний**, Автоматизация, **Отчёты**, **Тариф**, Управление, Настройки.

### 3.3 Ядро записи
- Идемпотентное создание записи, **защита от двойного бронирования на уровне БД** (exclusion constraint, а не проверкой в коде).
- Перенос/отмена с историей, outbox-событиями и аудитом.
- Проверка слота против живого расписания врача (отпуска, занятые окна).

### 3.4 Операционные воркеры (`/api/cron/workers`, `src/lib/`)
Один идемпотентный проход (порядок важен): **no-show** → **напоминания** → **закрытие брошенных диалогов записи** → **лист ожидания** → **перенос в МИС** → **outbox** → **доставка уведомлений**.
- **Уведомления** (`notifications/`): очередь с повторами и экспоненциальным backoff, рендер шаблонов RU/KK/EN, журнал попыток, статус `blocked` без учётных данных провайдера (не теряется и не выдаётся за отправленное). Каналы: portal / SMS / WhatsApp / Telegram / email.
- **Лист ожидания** (`scheduling/waitlist.ts`): подбор освободившегося слота в окне пациента, срок жизни предложения, приём/отказ из портала без двойной записи.
- **No-show** (`scheduling/no-show.ts`): закрывает пропущенный визит, ставит задачу сотруднику, уведомляет пациента.
- **MIS-sync** (`integrations/mis-sync.ts`): асинхронный перенос записи в DamuMed через outbox с **перечитыванием после сохранения**; отправленная, но не перечитанная запись не отправляется повторно (иначе дубль) — уходит в задачу человеку. Режим `remote` — очередь забирает внешний воркер (`/api/mis/queue`, `/api/mis/results`) под `MIS_WORKER_SECRET`.

### 3.5 Escalation Engine (передача человеку)
- Классификатор `src/lib/ai/escalation.ts`: причины `emergency / complaint / human_request / sensitive_data / no_slot / out_of_scope / identity_unverified`, распознавание intent, приоритет. RU/KZ/EN.
- Таблица `escalations` + карточка в «Операциях»: сводка, intent, причина, **что AI уже сделал**, контекст пациента с **маскированным телефоном**. Дедуп на разговор. API `/api/escalations/[id]`. Автосоздание из чата.

### 3.5.1 Разговорный booking-flow (`src/lib/booking/`, `src/lib/dal/booking.ts`)
AI ведёт пациента к записи и **фиксирует исход каждой попытки** — это то, чего не хватало для честных lost-reasons.

- **Движок** `booking/flow.ts` — чистая функция без IO: `need_doctor → need_slot → confirming → done`. Понимает «второй», «в 14:30», «завтра», «не надо в 9, давайте в 10» (решающим считается последнее названное время), различает отказ по цене и отказ от записи, переключает язык RU/KZ/EN и держит его.
- **Исход пишется в момент, когда произошёл**: `booked` / `lost` (`no_slot`, `price`, `no_doctor`, `changed_mind`, `wrong_time`, `identity_unverified`, `abandoned`) / `escalated`. Таблица `booking_sessions`, ограничение БД: причина потери существует ровно тогда, когда исход — потеря.
- **Бронирование идёт общим идемпотентным путём** (`createAppointmentForTenant`), поэтому защита от двойной записи та же. Если слот заняли между показом и подтверждением — пациенту предлагаются оставшиеся, а не сообщается об успехе. «Вы записаны» звучит только после подтверждения базой.
- **Обещания становятся строками**: при `no_slot`/`wrong_time` пациент реально попадает в `waitlist_entries`, и воркер листа ожидания подхватывает его в том же прогоне.
- Экстренный случай, жалоба и просьба о человеке прерывают запись и создают карточку эскалации с распознанной причиной.
- Два хода подряд без продвижения закрывают диалог честно: подбор врача уходит человеку, подбор времени — в лист ожидания.
- Поверхности: `POST /api/booking` (ход диалога), `GET /api/booking` (сессии), карточка «Диалоги записи» в «Операциях». Голос и MCP пока не подключены — движок каналонезависим, `runBookingTurnForTenant` принимает tenant напрямую.

### 3.6 Аналитика (директорская)
- **Выручка** (`dal/analytics.ts` → «Отчёты»): завершённые визиты × цена услуги, воронка (диалоги → записи → завершено → конверсия), «Куда уходит спрос» (неявки/отказы/истёкшие предложения/отмены с оценкой ₸). Помечено «оценка снизу».
- **«Почему пациенты не записались»** — отдельная панель с **точными** причинами из booking-flow: причина зафиксирована в момент отказа, а не выведена из отмен. Деньги — минимальная опубликованная цена услуг специальности врача (оценка снизу, помечена).
- **Intent Engine**: распознанный intent сохраняется на сообщениях; распределение обращений + языки в «Отчётах».
- **Автономия AI**: доля диалогов без передачи человеку + открытые эскалации.

### 3.7 Patient Identity (`ai/identity.ts`, `dal/identity.ts`, `/api/patients/verify`)
Подтверждение личности = телефон + второй фактор (фамилия или дата рождения). **По одному имени пациент не находится.** LIKE-метасимволы экранированы. Возвращает только статус, без данных пациента. Готов для пациентских каналов; в staff-чат намеренно не форсится.

### 3.8 Clinic Knowledge Engine (`ai/knowledge-rules.ts`, `dal/knowledge-rules.ts`)
Структурированные `knowledge_rules` (category / scope / keywords / priority) вместо одного гигантского промпта. Матчер достаёт адресное правило под intent, встроен в грудинг ассистента. Управление в разделе «База знаний».

### 3.9 Billing / white-label
`/portal/billing`: тарифы, живые счётчики потребления против лимитов, бренд клиники (название, цвета, логотип, контакты) в портале и текстах. Списание денег — вне AI Dos, пока не задан `BILLING_PROVIDER`.

### 3.10 Безопасность и мультитенантность
RLS на всех таблицах; авторизация (`requireRoles`/`requireUser`) на всех роутах; секреты только на сервере; сессии HttpOnly-cookie; аудит действий; ИИН минимизирован и не отправляется модели.

## 6. Осознанные границы (что НЕ сделано намеренно)

- **Две панели причин, и это осознанно.** «Куда уходит спрос» остаётся деривативной оценкой по неявкам/отменам/истёкшим предложениям — она покрывает спрос, потерянный вне разговора. «Почему пациенты не записались» — точные причины из booking-flow. Смешивать их в одну цифру нельзя: у них разная природа и разная достоверность.
- **Деньги за несостоявшуюся запись — оценка снизу**: минимальная опубликованная цена услуг специальности врача. Услуга в разговоре пока не выбирается, поэтому точного чека нет; если цен в прайсе нет — суммы нет, а не выдуманное среднее.
- **Identity не форсится в текущем чате** — он operator-facing (сотрудник, не пациент). В booking-flow путь `identity_unverified` реализован и сработает, как только появится пациентский канал без известного `patientId`.
- **Booking-flow не подключён к голосу и MCP** — движок каналонезависим (`runBookingTurnForTenant`), но проводка в Gemini Live / MCP-инструменты не сделана.

## 7. Куда двигаемся дальше (роадмап)

Приоритет сверху вниз. Многое из V1/V2 уже готово (см. раздел 3).

### Ближайшее (высокая ценность, честно строится сейчас)
1. ✅ **Живой разговорный booking-flow** — построен (раздел 3.5.1). Осталась проводка в пациентские каналы: голос (Gemini Live tools) и MCP-инструмент записи поверх того же движка.
2. **Urgent Booking Engine**: `NO_SLOT` → запрос администратору `APPROVE / DECLINE / OFFER 18:30`, AI продолжает диалог с пациентом. Теперь есть куда встроить: исход `no_slot` в booking-flow — точка входа.
3. **Enforcement идентификации в пациентских каналах** (голос/MCP/веб-виджет): перед выдачей данных о записи/результатах — обязательное подтверждение. Путь `identity_unverified` в booking-flow уже есть.

### Требует внешних доступов владельца
4. **DamuMed live-интеграция** — официальный API/credentials (контур async-переноса готов, ждёт доступ).
5. **Телефония + WhatsApp** — аккаунты BSP/Meta Cloud API, номер E.164, KYC, одобренные шаблоны RU/KZ. Каналы в коде готовы, включаются переменными окружения.

### V3 (после стабилизации ядра)
6. **Outbound AI**: подтверждение визита, обзвон листа ожидания при освобождении слота, recall.
7. **QA разговоров / Call Quality Score**: анализ intent, resolution, sentiment, policy compliance, риск галлюцинаций.
8. **Referral processing**: пациент шлёт фото/PDF направления → извлечение → booking.
9. **Multi-clinic / network slot search**: один AI ищет слот по всей сети филиалов.

### V4 (operational intelligence)
10. Прогноз спроса, оптимизация загрузки, revenue intelligence на исторических данных, network optimization, другие HIS.

### Что НЕ строить сейчас (защита от feature creep)
Медицинский AI-диагност, полноценная CRM/HIS, приложение пациента, огромный omnichannel, predictive analytics, insurance engine, телемедицина.

## 8. Внешние гейты перед боевым запуском с пациентами

Технически код в production-состоянии, но для **реальных пациентов** нужно (вне контроля разработки):
- **Юридическое**: политика конфиденциальности, сроки хранения, правовые основания обработки медданных.
- **DamuMed**: официальный доступ.
- **Телефония/WhatsApp**: провайдеры, номер, KYC, шаблоны.
- **Эксплуатация**: бэкапы БД, нагрузочное тестирование, пентест, on-call.
- **Vercel**: план Hobby ограничивает cron суточной частотой; для 15-минутных воркеров нужен Pro или внешний планировщик, дёргающий `/api/cron/workers` с `CRON_SECRET`.

AI Dos **не ставит диагнозы** и не является медицинским изделием.

## 9. Как запустить локально

```bash
npm install
cp .env.example .env.local   # заполнить DATABASE_URL, SESSION_SECRET и т.д.
npm run db:migrate
npm run dev
```

Ключевые переменные окружения — в `.env.example` (БД, сессии, OpenAI/Gemini, cron, каналы уведомлений, MIS worker, billing). Секреты — только в `.env.local` и в переменных Vercel.
